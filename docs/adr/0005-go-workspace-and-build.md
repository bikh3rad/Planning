# ADR 0005 — Go workspace & build tooling

**Status:** Accepted
**Date:** 2026-05-02
**Deciders:** Solution architecture
**Supersedes:** [ADR 0001](./0001-monorepo-tooling.md)

## Context

ADR 0001 chose pnpm + Turborepo for a TypeScript / NestJS monorepo. The implementation language has since been changed to Go. We need a fresh decision for Go workspace structure and build orchestration.

Forces:

- 7 backend services sharing significant internal code (event contracts, postgres helpers, crypto, observability)
- Small team — operationally simple beats theoretically optimal
- Go's standard tooling (`go build`, `go test`, build cache) is already excellent
- Mobile and web apps live in separate repos (see [14-tech-stack.md](../architecture/14-tech-stack.md)); this ADR scopes only the backend
- Cross-language contracts are needed (web + mobile consume them), but the contract layer is solved separately by protobuf + buf

## Decision

Use **a single Go module** with Go's standard build tooling, orchestrated by **Taskfile** (`task`). Seed the implementation from [`mequq/go-template`](https://github.com/mequq/go-template) and adopt its service-internal conventions wholesale; replicate them across N services within the single module.

Concretely:

- One `go.mod` at the repo root for the entire backend monorepo
- Per-service entrypoints under `cmd/<service>/main.go`, with a per-service Wire composition root at `cmd/<service>/wire.go` (build tag `wireinject`) that generates `cmd/<service>/wire_gen.go`
- Per-service domain code lives under `services/<service>/internal/{biz,repo,service,datasource,entity,mocks}/` — Go's positional `internal/` rule prevents any other service from importing it, enforcing service isolation at the language level
- Shared cross-service infrastructure under the repo-level `internal/<package>` (see "Service-internal stack" below) — Go's `internal/` rule confines these to this module
- `Taskfile.yml` declares build / test / lint / migrate / generate / run tasks per service
- Per-service Dockerfiles `COPY` only what they need; `go build` produces a static binary deployed in a distroless image
- CI uses `go test ./...` with the GitHub Actions Go-build-cache action

### Service-internal stack (adopted from the template)

Every service inside the module follows this layered structure (clean architecture):

| Layer | Tooling | Notes |
| --- | --- | --- |
| Composition root (per service) | **Google Wire** | Build tag `wireinject`; `wire_gen.go` is generated, never hand-edited |
| Runtime infrastructure | Shared `internal/app` package | `Application` lifecycle, `HTTPServer` (with `otelhttp` + recovery), `Controller` (Start / Shutdown / Healthz registry), `KConfig`, `AppLogger`, `OTLP` |
| HTTP wiring | stdlib `net/http.ServeMux` (Go 1.22 routing) | Same router as the template; no `chi` |
| HTTP handlers | `services/<svc>/internal/service/handler` | Each handler implements `service.Handler`; routes self-register on the shared mux |
| Use cases | `services/<svc>/internal/biz` | Interfaces named `Usecase…` (consumed by handlers); `Repository…` interfaces (implemented by `repo`) |
| Repositories | `services/<svc>/internal/repo` | Bound to use-case `Repository…` interfaces via `wire.Bind` |
| Datasources | `services/<svc>/internal/datasource` | DB / queue clients; each registers its own healthz + shutdown hooks on the shared `Controller` |
| Domain types | `services/<svc>/internal/entity` | Plain structs |
| Mocks | `services/<svc>/internal/mocks` | Generated by **mockery** (config in `.mockery.yaml`); mocks the `biz` package's interfaces |
| Config | **koanf** | YAML file (`--config` flag) overlaid with env vars prefixed `APP_` (`APP_FOO_BAR` → `foo.bar`) |
| API docs | **swag** | Annotations on handlers; UI mounted at `/swagger/`; spec at `/docs/swagger/swagger.json` |
| Postgres wrapper | `pgx` + `otelsql` | Tracing on every query without per-call instrumentation |

Dependency direction (per service): `cmd → app → service/handler → biz → repo → datasource → entity`. Anything that violates this is a smell.

### Repository layout

```
trustc-platform/
├── cmd/<service>/                 # main + wire composition root per service
│   ├── main.go
│   ├── wire.go                    # //go:build wireinject
│   └── wire_gen.go                # generated
├── services/<service>/
│   └── internal/                  # service-private — only cmd/<service> can import
│       ├── service/
│       │   ├── handler/           # HTTP handlers (implement service.Handler)
│       │   ├── dto/               # request / response shapes
│       │   └── server.go          # HTTP wiring + /metrics + /swagger
│       ├── biz/                   # use cases (Usecase…, Repository… interfaces)
│       ├── repo/                  # repository implementations
│       ├── datasource/            # DB / queue clients (per service if needed)
│       ├── entity/                # domain types
│       ├── mocks/                 # mockery-generated
│       ├── policies/              # service-local invariant guards
│       └── events/                # service-local event payload definitions
├── internal/                      # cross-service shared infrastructure
│   ├── app/                       # Application, HTTPServer, Controller, KConfig, AppLogger, OTLP — shared by every service
│   ├── event/                     # envelope, canonical-JSON, signing, validation
│   ├── contracts/                 # protobuf-generated Go types
│   ├── crypto/                    # ed25519, sha256 helpers
│   ├── pgx/                       # connection helpers, RLS context setter, migration runner, otelsql wiring
│   ├── nats/                      # JetStream client, outbox relay
│   ├── otel/                      # tracer / meter / logger setup
│   ├── httpx/                     # required-headers middleware, response envelope, error mapping
│   └── testing/                   # invariant test runners, fixtures, builders
├── pkg/middlewares/               # external-importable per-route HTTP middlewares
├── contracts/                     # .proto source of truth
├── infrastructure/{terraform,kubernetes,docker}/
├── tools/{codegen,policy-cli,replay}/
├── migrations/                    # per-service subdirs: migrations/<service>/000001_*.{up,down}.sql
├── docker-compose.yml             # local dev stack (Postgres, Redis, NATS, monitoring)
├── Taskfile.yml
├── .mockery.yaml
├── .golangci.yaml
├── go.mod
└── go.sum
```

Component lifecycle pattern: each datasource / handler / use case calls `Controller.RegisterStartup`, `RegisterShutdown`, and `RegisterHealthz` rather than being orchestrated centrally. Healthz fans out concurrently across registered checks; the `biz.healthz` use case aggregates results.

## Alternatives considered

### Workspace structure

- **Multi-module with `go.work`** (each service has its own `go.mod`)
  - Pros: per-service dep isolation, easier to extract a service to its own repo later
  - Cons: more ceremony for shared internal packages; `gopls` historically slower with workspaces; the `internal/` rule has subtle interactions across multiple modules
  - **Reject for v1** — single-module is simpler at our scale, and "split later" is a directory move plus dep cleanup, not a rewrite
- **Bazel (`rules_go`)**
  - Pros: hermetic, multi-language, excellent caching at scale
  - Cons: enormous operational weight; team has no Bazel experience; same reasoning that rejected it for the TS stack in ADR 0001
  - **Reject**
- **Polyrepo, one repo per service** (one `mequq/go-template` clone each)
  - Pros: matches the template's intended unit of deployment; fully independent deploys
  - Cons: shared internal code becomes a publishing problem; cross-cutting changes turn into N PRs; CI / observability config duplicated; first cross-cutting refactor reveals the cost
  - **Reject** — premature for our team size; we get the same blast-radius benefit from per-service Dockerfiles

### Build orchestration

- **Make + dagger** (the template's choice)
  - Pros: dagger gives portable CI-equivalent local builds in containers; Make is universally understood
  - Cons: Make has cross-platform issues (Windows contributors); dagger adds a Docker-in-Docker dependency for casual local builds
  - **Reject as primary orchestrator** for this monorepo; we may still adopt dagger pipelines for CI parity later as a layer on top of Taskfile
- **Mage** (Go-native task runner)
  - Pros: tasks written in Go, no extra binary
  - Cons: tasks become Go code that compiles; harder for non-Go contributors to read
  - **Reject** in favor of Taskfile, which is YAML and self-documenting

### Service-internal conventions

- **Hexagonal layout from scratch** (no template seed)
  - Pros: no inherited assumptions to undo
  - Cons: every layer's choice (DI library, config library, mocks, API docs, lifecycle pattern) re-litigated; each one is a small decision but the cumulative cost is real
  - **Reject** — `mequq/go-template` already makes coherent choices we agree with; reinventing them adds no value
- **Manual constructor injection instead of Wire**
  - Pros: no codegen step, easier to read for someone new to Wire
  - Cons: composition root grows quickly with 7 services and many dependencies; refactors become painful; we lose Wire's compile-time validation
  - **Reject** — adopt Wire, accept the codegen step
- **`chi` router instead of stdlib `ServeMux`**
  - Pros: more middleware ecosystem
  - Cons: stdlib `ServeMux` got pattern matching in Go 1.22; the template's middleware needs are met via `pkg/middlewares` and `otelhttp`
  - **Reject** — stay with stdlib, matching the template
- **OpenAPI-first with `oapi-codegen`** instead of swag annotations
  - Pros: spec is the source of truth, can be authored by non-Go contributors
  - Cons: extra friction adding a handler (edit YAML, regenerate, edit handler) vs annotating directly; the team is small enough that drift is unlikely
  - **Reject for v1** — adopt swag (code-first); revisit if non-Go consumers need to edit the spec directly

### Query layer (deliberate addition to the template)

- **`sqlc` generated queries on top of `pgx`**
  - The template uses raw `pgx` queries; we add `sqlc` because financial code benefits from compile-time-checked SQL types, and the cost is one codegen step per migration
  - This is additive, not a delta — `sqlc` produces `pgx`-compatible code that fits cleanly inside `services/<svc>/internal/repo/`

## Consequences

### Positive

- New contributors clone one repo, run `task up`, and have the full backend locally
- `go build ./cmd/<service>` produces a deployable binary using the standard build cache
- `go test ./...` runs every test in parallel; CI is fast without extra caching infrastructure
- `internal/` packages cannot be imported by anything outside the module — the language enforces the boundary that ADR 0001 needed Turborepo + pnpm strict mode to approximate
- Shared cross-cutting code lives in one place, versioned with the services that use it

### Negative

- Single `go.mod` means a transitive-dep update affects every service's image
  - Mitigated by `govulncheck` in CI and Go's typically small dep trees
- Splitting a service into its own repo later is a directory move plus dep cleanup, not a one-liner
- Taskfile is one more tool to learn, but it's YAML — shallow curve

### Migration discipline

- **No service writes outside its own service's DB schema.** The single Go module does not relax the schema-isolation rule from [02-domains.md](../architecture/02-domains.md).
- **No business-logic helpers in `internal/`.** Only protocol, transport, and observability utilities. Cross-domain types are forbidden.
- **`go mod tidy` runs in CI** — undeclared deps fail the build.
- **`wire_gen.go` is generated; never hand-edit.** Modify the relevant `wire.go` provider set and run `task generate`.
- **Mocks regenerate on every change to `internal/biz` interfaces** — `task generate` invokes mockery; a stale mock that doesn't match an interface is a CI failure.

### Revisit when

- A service's dep set genuinely conflicts with another's (Go's flat dep model handles this fine for internal-only deps; conflicts arise only with C-bound libraries, which we avoid)
- We approach 30+ services or 50+ engineers — at that point, revisit Bazel or polyrepo
- Build / test wall-clock time exceeds 10 minutes despite caching
